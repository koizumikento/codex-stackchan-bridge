# StackChan Setup Workflow

Use this skill to set up a local codex-stackchan-bridge environment without
crossing the project's local-first and safety boundaries. Prefer repo helpers
and documented smoke commands over ad hoc setup steps.

## Do Not Use For

- Implementing new commands, ROS interfaces, bridge behavior, firmware features,
  or Codex product skill behavior. Use `stackchan-dev-workflow`.
- Contract, topic, service, action, command metadata, or result-shape changes.
  Use `stackchan-contract-change`.
- Choosing validation gates after code edits. Use `stackchan-quality-gates`.
- Servo calibration writes, raw hardware controls, or maintenance unlocks
  unless the relevant setup doc explicitly requires an operator-confirmed path.

## Start Here

1. Read the root `AGENTS.md`.
2. Read `docs/README.md`, then choose the closest setup docs:
   - Local architecture and boundaries: `docs/architecture.md`
   - CLI/backend setup and mock checks: `docs/stackchanctl.md`
   - ROS 2 container setup: `docs/ros2-container.md`
   - Physical K151 bring-up: `docs/hardware-validation.md`
   - Local speech/TTS setup: `docs/speech-design.md` and the TTS sections in
     `docs/hardware-validation.md`
   - Validation expectations: `docs/quality-gates.md`
3. Inspect `git status --short` before running setup commands so generated or
   user changes are not mistaken for setup output.

## Choose Setup Mode

Ask at most one short clarification if the target mode is unclear. Otherwise,
pick the smallest useful mode:

- `mock-only`: stackchanctl and Codex skill behavior without ROS 2 or hardware.
- `ros2-container`: build/check stackchan_msgs and stackchan_bridge in the
  documented ROS 2 Jazzy container.
- `hardware-k151`: physical M5StackChan K151 over micro-ROS serial or the
  Windows host serial TCP bridge.
- `local-tts`: optional local TTS provider setup, usually VOICEVOX, without
  vendoring engines or exposing provider raw IDs.

## Workflow

1. Confirm prerequisites for the selected mode, such as `uv`, Docker Desktop,
   a usable serial port, or an operator-owned local TTS service.
2. Use repository helpers first:
   - Python/CLI checks: `uv run --directory apps/stackchanctl ...`
   - ROS interface checks: `uv run --no-project python scripts/check_ros_interfaces.py`
   - ROS 2 container smoke: `uv run --no-project python scripts/ros2_container.py smoke`
   - micro-ROS Agent/container helpers: `uv run --no-project python scripts/microros_agent_container.py ...`
   - Serial bridge: `uv run --no-project --with pyserial python scripts/serial_tcp_bridge.py ...`
   - Firmware plan/upload: `uv run --no-project python scripts/firmware_platformio.py ...`
3. For hardware-free setup, verify mock behavior before bridge or firmware:
   - `uv run --directory apps/stackchanctl python -m unittest discover -s tests`
   - `uv run --directory apps/stackchanctl --with ruff ruff check .`
   - `stackchanctl --backend mock observe --json`
   - `stackchanctl --backend mock doctor --json`
4. For ROS 2 setup, prefer documented container helpers over installing ROS 2
   directly on the host.
5. For Windows hardware setup, treat Docker Desktop serial access as suspicious
   until proven. Prefer the documented host serial TCP bridge when container
   serial passthrough is unreliable.
6. For firmware setup, use `scripts/firmware_platformio.py plan` before upload.
   Use direct flashing tools only for documented recovery or diagnostics.
7. For local TTS, keep engines and voices operator-owned. Use bridge-owned
   profile names in commands, never provider raw speaker IDs or secrets.

## Output

- State the selected setup mode and why.
- List exact commands run, their result, and any unavailable checks.
- Report local paths changed or generated by setup.
- For hardware, record device id, port, baud, firmware profile, and smoke result
  codes without logging speech text, PCM, images, NFC tag IDs, IR codes, or
  secrets.
- End with the next one to three setup actions, especially any operator-only
  hardware or listening checks.

## Guardrails

- Keep the standard control path as `stackchanctl -> stackchan_bridge facade ->
  firmware`.
- Codex-facing setup should call `stackchanctl`, not raw `ros2` commands. Raw
  ROS tools may be used only for documented diagnostics and bring-up isolation.
- Do not add cloud accounts, mobile-app dependencies, ad hoc network APIs, or
  vendored TTS engines.
- Do not claim audible quality from `tts_finished`, action completion, or drain
  events alone. Audible quality needs an operator-listening result.
- Do not print or paste sensitive payloads in logs, comments, or summaries.
